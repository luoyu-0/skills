# Git 交付

本 Skill 覆盖任务成果提交、创建 PR 和审核远程 PR。用户的明确要求、目标仓库的协作规范和现有 PR 模板优先于本 Skill。除非用户要求 PR，不主动创建 PR；除非用户要求合并，不主动合并。审核 PR 时可准备本地分支，但不因审核流程自动提交、推送或修改远程 PR。

## 任务完成时判断是否提交

先完成用户要求的修改与必要验证，再判断是否创建 commit。满足以下条件时，可将本 Skill 视为用户对**本轮任务成果**的持续自动提交授权：

- 本轮工作已完成，改动属于当前任务，且可清楚说明修改目的。
- 已检查 `git status`、差异和暂存内容；不夹带他人改动、密钥、生成的大文件或本地运行数据。
- 已执行与变更相称的验证；失败、未运行的检查及其影响能够如实说明。
- 用户没有要求暂缓提交；仓库规则没有要求每次提交前另行取得明确授权，也没有其他禁止提交的条件。

没有文件变更时不创建空 commit。任务未完成、改动归属不明或上述条件不成立时，保留现状并说明原因；需要用户决定时提出具体问题。提交应在本轮最终回复**之前**完成，最终回复说明提交哈希及验证结果。

仅暂存本轮任务相关文件。提交信息采用 `<type>(<scope>): <描述>`；`type` 根据实际改动选用 `feat`、`fix`、`docs`、`test`、`refactor`、`perf` 或 `chore`，`scope` 使用明确的模块名，描述使用用户或仓库规定的语言并说明实际成果。一个 commit 尽量只表达一个目的；若变更目的独立，分别提交。

## 用户要求 PR 时

1. 读取仓库协作规则、PR 模板和关联任务；核对目标分支、当前分支、完整差异及已有本地改动。先完成代码、文档和验证，再提交本轮成果并推送相应分支。
2. 调查 PR 的事实依据：变更前后的行为、关键实现、测试或人工验证结果、接口或数据结构变化、部署影响、兼容性与未决风险。关联 Issue 或外部资料只在确有相关性时查阅。将“已通过”“未运行”“失败”“尚待 CI”明确区分，不推测结果。
3. PR 标题沿用 `<type>(<scope>): <描述>`。优先遵循仓库模板；没有更具体模板时使用下列结构，并用简洁、可核对的事实填充：

   ```markdown
   ## 背景
   为什么需要修改。

   ## 主要变更
   - 实际完成的改动。

   ## 验证
   - 执行的命令、结果与必要的前后对比。

   ## 影响
   - API、数据、配置、部署和兼容性影响；没有则写“无”。
   - 尚未完成的验证或风险。
   ```

4. 创建指向用户指定目标分支的 PR；未指定时使用仓库默认分支。若任务明确仍未完成且适合评审，使用 Draft 并列出剩余事项。创建后核对 PR 链接、基分支、提交和检查状态，在最终回复中报告。不要把 PR 已创建说成 CI 已通过或已合并。

PR 描述要让审阅者仅凭描述理解变更、证据和影响。视觉变更在可获得时附截图；接口变化在可获得时附请求与响应示例。任何未实际验证的结论均标明待验证。

## 用户要求审核远程 PR 时

1. **确定审核对象与基准。** 读取 PR 标题、描述、关联任务、目标分支、来源仓库与来源分支、最新 head commit、完整文件差异、提交记录和 CI 状态；读取目标仓库的贡献规范、测试说明及相关代码。明确 PR 要解决的问题和预期行为，审核期间以同一 head commit 为准；若远程出现新提交，核对后重新审核受影响部分。
2. **准备同名本地分支。** 先检查本地工作区、现有分支和同名分支的状态，保留已有改动。按 PR 的来源仓库和来源分支获取代码，在本地使用与远程来源分支同名的分支；已有同名分支则复用，并确认其来源与 PR 一致。将该分支更新到所审核的 head commit，再核对本地 commit 与 PR 是否一致。若同名分支指向其他来源、存在未提交改动或更新会覆盖本地成果，先保护现场并说明冲突，不强制重置或覆盖。
3. **静态审核。** 相对 PR 的目标分支检查完整改动及上下文，逐项核对需求、正确性、边界条件、错误处理、兼容性、性能、安全性与项目约定。只将由本次改动引入、可定位且值得作者修复的问题列为审核意见；注明文件、行号、触发条件、影响和建议。
4. **验证实际效果。** 依照仓库说明在本地准备运行环境，执行与改动相关的测试、构建或静态检查，并实际运行受影响的功能或接口，观察用户可见行为和关键边界场景。必要时与目标分支的原行为对比，记录运行命令、环境、输入、输出及复现步骤。运行需要下载新依赖、接入外部服务或可能产生副作用时，遵守用户和仓库的授权要求；无法运行时说明具体阻碍与未验证范围，不把 CI 通过当作本地效果已验证。
5. **形成结论。** 结合静态审查和运行证据，按严重程度列出可执行的问题；无问题时明确说明已检查范围。区分已复现、推断风险和待验证事项，记录测试通过、失败、未运行及其原因，并给出总体审核意见。发布评论前重新确认 PR head 是否变化。
6. **先在会话中展示评论草稿。** 将拟发布到 PR 的 comment 原文及对应位置展示给用户，同时给出审核结论和验证证据，询问用户是否将这些 comment 发布到 PR。只有用户明确同意后，才向远程 PR 发布；用户要求修改草稿时先修改并重新展示。未获同意时，审核意见仅保留在会话中。
